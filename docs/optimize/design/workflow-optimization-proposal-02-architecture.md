# FlowMem Workflow 优化方案 v2.8 - 核心架构

## 2.1 检索分层：内置优先，ccq-engine 可选

**决策**: 默认使用工具内置检索，ccq-engine 作为可选增强层。

| 检索层职责 | Agent 职责 |
|-----------------|-----------|
| ✅ 工具内置检索（默认） | ✅ 需求分析与增强 |
| ✅ ccq-engine（可选增强） | ✅ 方案设计与对比 |
| ✅ 代码索引/语义搜索 | ✅ 任务分解与规划 |
| ❌ 检索层不做分析 | ✅ 代码实现与审核 |
| ❌ 检索层不做推理 | ✅ 综合判断与决策 |

**好处**:
- 默认不增加 API key 负担。
- 大仓库/跨会话场景可启用 ccq-engine 提升稳定性。

---

## 2.2 Agent 架构：Subagent 优先 + 可选多模型

**决策**: Claude Code 使用 Subagent 实现上下文隔离；允许 per-agent 指定模型/Key。

**为什么不用单模型多角色**:

| 问题 | 单模型多角色 | Subagent/多 Agent |
|------|-------------|------------------|
| 自我一致性偏见 | ❌ Reviewer 容易认可自己刚写的代码 | ✅ Reviewer 独立上下文交叉审核 |
| 方案质量 | ❌ 一次生成，无审核 | ✅ Solver + Critic 迭代打磨 |
| 上下文污染 | ❌ 共享上下文 | ✅ Subagent 独立上下文 |

**Agent 清单（7 个）**:

| Agent | 职责 | 调用时机 | 输入 | 输出 |
|-------|------|----------|------|------|
| **Orchestrator** | 流程控制、状态管理、用户交互 | 全程 | 用户请求 | 协调指令、最终输出 |
| **Analyst** | 需求分析、完整性评分、追问 | Phase 1.2 | 用户需求 + 代码上下文 | 评分 + 追问问题 |
| **Solver** | 方案设计 | Phase 1.3 | 需求 + 上下文 + Critic 反馈 | 技术方案 |
| **Critic** | 方案审核、找问题 | Phase 1.3 | 方案 + 需求 + 约束 | 通过/问题清单 |
| **Planner** | 任务分解、WBS、依赖分析 | Phase 2 | request.md | todolist.md |
| **Coder** | 代码实现 | Phase 3 | 单个 todo + 上下文 | 代码变更 |
| **Reviewer** | 代码审核、质量把关 | Phase 3 | 代码变更 + 验收条件 | 通过/拒绝 + 理由 |

**约束**:
- Orchestrator 留在主会话，避免再做一层 Agent。
- Subagent 只通过 `.agentmem/*` 交接产出。

## 2.3 方案迭代机制（Solver + Critic）

**决策**: 采用单方案迭代，最多 2 轮。

```
Solver 方案 V1 → Critic 审核 → Solver 修订 → Critic 再审 → 用户确认
```

**Critic 审核清单**:

| 类别 | 检查项 | 说明 |
|------|--------|------|
| **方向正确性** | 是否解决用户真正问题 | 方向错误比细节更严重 |
| **技术可行性** | 能否实现、有无技术障碍 | 考虑现有代码库约束 |
| **完整性** | 是否覆盖边界与异常 | 检查遗漏场景 |
| **风险点** | 性能/安全/兼容隐患 | 识别潜在问题 |
| **一致性** | 与现有代码模式一致 | 参考检索结果 |

**Solver vs Critic vs Reviewer**:

| Agent | 审核对象 | 审核时机 | 关注点 |
|-------|----------|----------|--------|
| **Critic** | 技术方案 | Phase 1 | 方向、可行性、完整性 |
| **Reviewer** | 代码变更 | Phase 3 | 质量、验收条件、偷懒检测 |

## 2.4 用户介入策略：最小介入

**原则**:
- AI 先整合，用户只确认结果。
- 介入点固定，避免频繁打断。
- 高风险/不可自动测试场景必须用户确认。

**固定介入点**:
- Phase 1 方案确认。
- Phase 2 规划确认。

**动态介入点**:
- 需求评分不足时追问。
- Reviewer 连续失败或高风险变更。

---

## 2.5 上下文隔离与通信

- Subagent 独立上下文 + 独立 loop，主会话只收摘要。
- 共享仅通过 `.agentmem/*` 文件传递。
- Background Subagent 不能使用 MCP 工具，涉及检索的任务需前台执行。

---

## 2.6 Per-agent 模型/Key 路由

**策略**:
- 有 key：使用对应模型。
- 无 key：回退默认模型/工具。
- 输出结构统一，降低跨模型差异。

---

## 2.7 Token 预算策略：Context Curator

**问题**: 大仓库任务容易超出主会话 token 限制。

**策略**:
- 设立 Context Curator（长上下文模型）只做"上下文打包"。
- 产出 `.agentmem/context.md`，其他 Agent 只读取该文件。
- 准确率提升需与内置检索/ccq-engine 对比验证。

**触发条件**（满足其一即触发）:

| 条件 | 阈值 | 说明 |
|------|------|------|
| 主会话 token 使用率 | > 60% | 预留空间给后续 Agent 交互 |
| 检索结果文件数 | > 15 个 | 文件过多需要筛选和摘要 |
| 跨目录数量 | ≥ 3 个顶级目录 | 跨模块任务需要统一上下文视图 |
| 单文件行数 | > 500 行 | 大文件需要提取关键片段 |
| 用户显式要求 | - | 用户输入"整理上下文"或类似指令 |

**不触发条件**（即使满足上述条件也跳过）:
- 极简路径任务
- 检索结果已高度相关（相关性评分 > 0.8）
- 用户显式禁用（`project.md` 中 `context_curator: false`）

**Context Curator 输出格式**:

```markdown
# 上下文摘要

**生成时间**: 2026-01-22T10:30:00Z
**任务**: [任务简述]
**Token 节省**: 约 X tokens (Y%)

## 关键文件

| 文件 | 行号 | 相关性 | 摘要 |
|------|------|--------|------|
| src/auth/login.ts | 45-120 | 高 | 登录逻辑主函数 |
| src/utils/token.ts | 10-50 | 中 | Token 生成工具 |

## 关键代码片段

### src/auth/login.ts:45-60
\`\`\`typescript
// 关键代码摘录
\`\`\`

## 依赖关系

- login.ts → token.ts (调用 generateToken)
- login.ts → db/user.ts (查询用户)
```
