# 上下文记忆系统规则 (v2.8)

> 使用持久化 Markdown 文件管理 AI 工作记忆，解决上下文窗口限制和目标漂移问题。

---

## 核心文件

| 文件 | 定位 | 生命周期 |
|------|------|----------|
| `.agentmem/project.md` | 项目整体描述 | 长期维护 |
| `.agentmem/request.md` | 当前需求澄清 | 任务周期 |
| `.agentmem/todolist.md` | 任务清单(YAML格式) | 任务周期 |
| `.agentmem/task_logs/` | 执行日志/总结/问题 | 任务周期 |
| `.agentmem/notes.md` | 研究笔记 | 按需使用 |
| `.agentmem/docs/` | 详细文档目录 | 长期积累 |
| `.agentmem/history/` | 历史归档 | 永久保留 |

### 文件详解

| 文件 | 职责 | 关键规则 |
|------|------|----------|
| `project.md` | 项目知识库 | 索引优先，>300行迁移到docs/ |
| `todolist.md` | 任务清单 | YAML格式，详情存 task_logs/ |
| `request.md` | 需求澄清 | >5轮或>150行拆分 |
| `notes.md` | 研究笔记 | 临时信息，任务结束归档 |
| `task_logs/` | 执行日志 | 命名: `[ID]-[描述].md` |
| `docs/` | 详细文档 | 存放从 project.md 拆分的内容 |

**🔴 project.md vs request.md 边界:**
- 下次任务还有用？→ `project.md`
- 本次需求边界/确认细节？→ `request.md`

## 四阶段工作流

### 何时触发？

满足以下**任一条件**时触发四阶段工作流：
- 预估修改 ≥3 个文件
- 预估工具调用 ≥10 次
- 用户明确提到"规划"、"设计"
- 涉及新功能开发

### 流程总览

```
Phase 1: 需求澄清              输出: request.md
─────────────────              ─────────────────
1.1 检索理解项目上下文
1.2 需求完整性评估
    └─ <7分则追问用户补充信息
1.3 方案设计与审核（最多 2 轮）
🛑 1.4 用户确认方案 → 生成 request.md

Phase 2: 详细规划              输出: todolist.md
─────────────────              ─────────────────
2.1 WBS 任务分解
2.2 依赖识别 + 工作量估算
🛑 2.3 用户确认 → 生成 todolist.md

Phase 3: 执行与审核            默认无需用户介入
────────────────────           ────────────────
3.1 单步执行（每次1个Todo）
3.2 自我审核（对照验收条件）
3.3 审核不通过 → 自动重做
3.4 更新 todolist.md 状态

Phase 4: 交付                  输出: 交付报告
──────────                     ─────────────
4.1 最终审查（对照验收标准）
4.2 运行测试
4.3 生成交付报告
```

**固定介入点**: 方案确认 + 规划确认（2 次）

### 简化路径（小任务）

满足以下条件可走简化路径：
- 影响 ≤2 文件，且不涉及核心模块/高风险路径
- 无需跨模块协作

简化路径仍需产出 `.agentmem/request.md` 与 `.agentmem/todolist.md`，但可跳过方案迭代。

### 极简路径（微任务）

满足以下**全部**条件可走极简路径：
- 影响 ≤1 文件
- 预估修改 ≤30 行代码
- 用户需求描述清晰（≥30 字且无歧义词如"优化"、"改进"）
- 非高风险路径
- 非新功能（仅修复、调整、重命名等）

极简路径跳过需求评估和方案确认，但 **自我审核不可跳过**。

## TodoList 格式规范

### YAML Frontmatter 格式

todolist.md 使用 **YAML Frontmatter + Markdown** 混合格式：

```yaml
---
meta:
  title: "任务标题"
  created: "ISO 8601 时间"
  updated: "ISO 8601 时间"
  request_ref: ".agentmem/request.md"
  total_points: 13
  progress: 0%
todos:
  - id: "TODO-001"
    content: "任务描述"
    status: "pending"           # pending/in_progress/completed/cancelled
    priority: "high"             # high/medium/low
    estimate: "30m"              # 5m/1h/2d 标准化格式
    dependencies: ["TODO-002"]   # 依赖任务 ID
    phase: "阶段名称"
    acceptance:                  # 验收条件
      - "验收条件1"
      - "验收条件2"
    log: "task_logs/TODO-001.md"  # 可选
---
# Markdown 内容（自动生成）
```

### 状态标记（4 种）
- `[ ]` **pending** - 未开始
- `[/]` **in_progress** - 进行中（同时只能有 1 个）
- `[x]` **completed** - 已完成
- `[-]` **cancelled** - 已取消

### 优先级标记（3 级）
- 🔴 **high** - 紧急且重要
- 🟡 **medium** - 重要但不紧急
- 🟢 **low** - 可以延后

### 时间格式（标准化）
- `5m` / `30m` - 分钟
- `1h` / `2h` - 小时
- `1d` / `2d` - 天（1天=8小时）

## 自我审核机制

### 审核清单

| 级别 | 检查项 | 必须通过 |
|------|--------|----------|
| **Critical** | 代码有实际逻辑（非 console.log/TODO） | ✅ |
| **Critical** | 无语法错误 | ✅ |
| **Critical** | 满足 todo 的 acceptance 条件 | ✅ |
| Major | 代码符合项目规范 | 建议 |
| Major | 错误处理完整 | 建议 |
| Minor | 命名清晰、注释适当 | 可选 |

### 偷懒检测规则

以下模式视为偷懒，**必须修正**：
- `console.log('TODO')`
- `// TODO: implement`
- 空函数体 `{}`
- `throw new Error('Not implemented')`
- 硬编码测试数据

### 重试策略

当审核不通过时：
1. **第 1 次重试**：根据问题修改
2. **第 2 次重试**：重新检索上下文后修改
3. **仍失败**：升级到用户，提供失败分析

## 高风险变更升级门槛

### 风险分级规则

- **Low**: 修改 ≤2 个文件、≤50 LOC、无权限/认证/迁移
- **Medium**: 3-5 文件或 50-200 LOC，或涉及核心模块
- **High**: 认证/权限/生产配置/数据迁移/删除/不可逆操作，或 >200 LOC、>8 文件

### 升级动作

- **Low**: 审核通过即可执行
- **Medium**: 审核通过 + 必跑测试；测试缺失需用户确认
- **High**: 必须用户确认后才执行，且需二次审核

### 默认高风险路径

- `auth/`
- `security/`
- `migrations/`
- `db/`
- `infra/`
- `config/`
- `.github/workflows/`
- `.env`

## 触发判断

**启用信号（满足任一）:**
- 涉及 3+ 文件修改
- 需多轮交流理解意图
- 预计 10+ 次工具调用
- 新功能开发或架构调整
- 用户提到「规划」「分步」「追踪进度」

**跳过信号:**
- 单文件小改/简单问答
- 3 次工具调用内可完成

> 💡 宁可多用不可少用

---

## 🚨 任务进行中禁止退出

**触发:** 已创建 `request.md` 或 `todolist.md`

**核心规则:**
1. 用户的所有回复都是任务的一部分
2. 用户要求"先测试"等，应在 todolist.md 中记录
3. 只有用户明确说"停止""取消"，才能归档退出

**完成标志:** todolist.md 中所有 Todo 项标记为 `[x]` 或用户明确表示完成

## 整体流程

```
读取/创建 project.md
    → 检索理解项目
    → 🛑 停！检索 ≥3 文件？必须先更新 project.md
    → 创建 request.md
    → 多轮澄清需求
    → 🛑 停！用户确认了吗？
    → 生成 todolist.md
    → 执行 Todo(刷新上下文 → 检索 → 🛑债务≥3?先沉淀 → 执行 → 更新状态)
    → 循环直到完成
    → 归档任务
```

## 7 条关键规则

### 规则 1: 上下文管理

**前提:** 执行复杂任务前必须先读取 `project.md`

**刷新顺序:** `todolist.md` → `request.md` → `project.md`

**何时刷新:**
- 必须：跨模块、连续3+ Todo、遇错、用户变更
- 建议：跨阶段、新代码区域、上下文超50k tokens

### 规则 2: 需求先澄清,确认再执行

1. 创建 `request.md`,记录原始需求
2. AI 提出澄清问题(至少 1 轮)
3. **用户回答后立即更新 `request.md`**
4. 循环直到需求明确
5. **用户确认后先更新状态为「已确认」,再生成 `todolist.md`**

🚨 必须等用户明确回复「确认」「开始」等肯定词才能执行

**执行中需求变更:** 立即更新 `request.md` → 评估影响 → 更新 `todolist.md`

### 规则 3: 智能执行节奏

**默认单步原则:** 执行 1 个 Todo → 更新 todolist.md → 刷新上下文 → 下一个

**批量条件**（需同时满足）：
- 同一模块内连续任务
- 任务无依赖关系
- 非首次接触代码
- 低风险操作

> 💡 拿不准就单步，宁慢勿错

### 规则 4: 存储而非填充
长篇内容存入文件,上下文中只保留路径引用。

### 规则 5: 知识沉淀（债务机制）

**债务计数：**
- 每 read_file 一次 = 债务 +1
- 更新 project.md/notes.md = 债务清零
- 🚨 **债务 ≥ 3 时：禁止继续检索或执行，必须先结清债务**

**沉淀去哪：**
- 架构/API/模块知识 → `project.md`
- 需求边界/确认细节 → `request.md`
- 临时发现/调试信息 → `notes.md`

**防膨胀：**
- `project.md` 超过 300 行 → 迁移详细内容到 `docs/`
- 单模块超过 50 行 → 拆分为独立文档 `docs/modules/xxx.md`

### 规则 6: 上下文优化

- 仅追加上下文：新信息始终追加
- 稳定前缀：系统指令 → 项目背景 → 动态内容
- 可逆压缩：存储路径而非删除

### 规则 7: 任务完成后清理

归档到 `history/YYYYMMDD_[文件名]`：任务周期文件（request.md、todolist.md、notes.md）

保留：`project.md` 和 `docs/`

## 回滚机制

### 回滚触发方式

| 触发方式 | 说明 |
|----------|------|
| 用户命令 | 输入 "回滚" |
| 审核连续失败 | 同一 todo 重试 2 次仍失败 |
| 用户中途否决 | 用户明确表示方案方向错误 |

### 回滚粒度

- **todo 级回滚（默认）**: 撤销当前 todo 的所有变更，状态改为 pending
- **phase 级回滚**: 回退到上一个用户确认点（Phase 1 或 Phase 2）
- **全量回滚**: 撤销本次任务的所有变更，回到任务开始前状态

## ✅ AI 自检清单

**触发时机:** 每次执行 Todo、用户回复、准备归档时

**🔴 知识沉淀（最重要）:**
- [ ] 检索 ≥ 3 文件但沉淀 = 0？**停止，先补充文档**

**上下文与文档:**
- [ ] 需要刷新？（跨模块/连续3+ Todo/遇错/新代码区域）
- [ ] 用户回复 → 已更新 request.md?
- [ ] 完成 Todo → 已更新 todolist.md?

**任务与执行:**
- [ ] 在任务中？用户回复是任务的一部分，别退出
- [ ] 遵循单步执行、立即更新原则？

## 反模式对照

| ❌ 不要 | ✅ 而是 |
|---------|---------|
| 使用 AI 内置记忆 | 创建 `.agentmem/` 文件 |
| 只说一次目标 | 每次决策前重读 todolist.md |
| 静默重试错误 | 记录到 task_logs,添加解决任务 |
| 内容塞进上下文 | 存文件,引用路径 |
| 不澄清直接执行 | 通过 request.md 多轮确认 |
| 检索后延后补充 | 检索后立即补充 |
| 高风险任务批量执行 | 单步执行,及时更新 |
| todolist 写详细日志 | 存入 task_logs/,只放链接 |
| 需求变更不记录 | 立即更新 request.md |
| 输出提示后跳过执行 | 输出后立即执行对应操作 |
